## Causa isolata

La catena modello-server è corretta. Il loop nasce dalla combinazione di:

1. una pseudo-tool-call testuale `finish(message=...)` già presente nella history;
2. il comportamento nativo di OpenHands, che considera una risposta testuale non vuota una
   terminazione valida della conversazione;
3. il precedente Stop hook v0.6.2, che dopo il deny chiedeva nuovamente di "Call native finish";
4. Qwen che, nel contesto contaminato, imitava la pseudo-call precedente invece di produrre una
   tool call strutturata.

Il risultato era un ciclo Stop deny -> pseudo-finish testuale -> CONTENT/FINISHED -> Stop deny.

## Audit native/installabile prima della correzione

Prima di aggiungere logica al plugin sono stati verificati i meccanismi nativi disponibili:

- OpenHands supporta sia FinishTool sia risposta testuale finale.
- Il FinishTool è realmente presente nel toolset del parent.
- Non è emerso un controllo nativo adatto a imporre tool_choice=required soltanto nel turno
  successivo a uno Stop deny.
- Il percorso API/eventi esiste, ma una chiamata HTTP sincrona allo stesso Agent Server dal
  callback Stop non è appropriata; il runtime espone già la persistenza eventi locale.
- Un precedente fix upstream per loop ripetuti di Stop denial non risulta integrato nella
  versione in uso.

## Correzione v0.6.3

Il ramo terminal failure conserva due percorsi validi:

1. native FinishTool: il percorso v0.6.2 resta accettato e produce
   `proof=PostToolUse:finish`;
2. normale risposta finale OpenHands: lo Stop hook legge l'ultimo MessageEvent agent dalla
   persistenza locale e lo accetta soltanto se il testo coincide esattamente con il
   `BIBLIOTECARIO_FAILURE: <phase>: <reason>` derivato da TERMINAL_FAILURE.json.

Nel secondo caso viene scritto `FAILURE_REPORT.json` schema 2 con:

- `proof=Stop:verified-agent-message`;
- hash SHA-256 del TERMINAL_FAILURE corrente;
- event_id del MessageEvent verificato;
- messaggio canonico esatto.

Pseudo-call testuali, success claim e report stale restano negati.

## Invarianti mantenuti

- Nessun PASS dipende dalla dichiarazione dell'LLM.
- TERMINAL_FAILURE.json resta la fonte deterministica del fallimento.
- Nessuna modifica a OpenHands/Agent Canvas upstream.
- Nessuna modifica ai GGUF, ai template o ai parser.
- Parent profile rev10 invariato.
- Planner/executor/reviewer e validazione deterministica invariati.

## Rischio residuo

OpenHands può ancora terminare per esaurimento del budget/max-iterations dopo ripetuti Stop deny.
La v0.6.3 elimina il loop riprodotto in questa diagnosi fornendo una terminazione testuale nativa
che Qwen ha già superato nel test contaminato, ma non può trasformare il limite upstream in una
garanzia assoluta contro un modello indefinitamente non cooperativo.
